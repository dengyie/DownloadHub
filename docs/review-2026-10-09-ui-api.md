# Findings

## [P1] 验卡与签发并发会丢失已经扣次凭证的恢复入口（已修复）

- 文件与位置：frontend/src/pages/redeem.js：renderResults、submit 和下载按钮事件
- 所属维度：正确性、并发、状态生命周期
- 问题：按钮各自禁用不足以保护整个资源列表；验卡响应可以替换仍在等待签发响应的列表。
- 触发条件：签发已在服务器完成但响应尚未到达时重新验卡，或重新验卡期间点击旧资源签发。
- 实际影响：旧 credential 脱离页面；最后一次额度已扣除时，用户可能无法从页面恢复该授权。
- 根本原因：签发是不可撤销的服务端操作，列表替换却没有与它共享页级状态。
- 最小修改方案：已增加 checkingCard 与 pendingGrants 集合，只互斥验卡/列表替换与签发，不取消已发出的签发操作，不阻塞不同资源的正常并发。
- 需要补充的测试：两项延迟真实浏览器响应回归已红转绿；另验证失联后使用同一 credential、quota=0 恢复和失败验卡保留列表。
- 是否阻塞合并：修复前阻塞；当前已有对应验证，不再构成代码阻塞。

## [P1] 结算表单重建使填写验证码后的首次支付点击丢失（已修复）

- 文件与位置：frontend/src/pages/product.js：结算表单事件和 updateReadiness
- 所属维度：正确性、用户流程、DOM 生命周期
- 问题：输入失焦的 change 处理重建了支付按钮，发生在 mousedown 与 click 之间。
- 触发条件：用户填完最后一个验证码字段，直接点击创建订单。
- 实际影响：第一次点击不会下单，用户需再次点击；依赖异步更新的表单也容易失去正在操作的节点。
- 根本原因：整段重建 DOM 被用来刷新按钮状态，状态更新与事件目标生命周期耦合。
- 最小修改方案：已保持结算按钮节点稳定，仅更新其文案、disabled 和状态；提交期间按同一状态锁防重复，不新增自动重试。
- 需要补充的测试：浏览器 checkout 场景填写验证码后一次真实点击即创建订单，并断言 tradeCount=1；失联场景不产生第二单。
- 是否阻塞合并：修复前阻塞；当前已有对应验证，不再构成代码阻塞。

## [P2] 无时区的商城抢购时间被按顾客本地时区解析（已修复）

- 文件与位置：frontend/src/commerce-model.js：saleTime、purchaseRestriction；固定 PHP kernel/Kernel.php
- 所属维度：正确性、接口合同
- 问题：Date.parse 把 PHP SQL 日期当成本地时间，而后端显式设置 Asia/Shanghai。
- 触发条件：顾客的设备不在北京时间时区并访问限时商品。
- 实际影响：UTC 测试复现 8 小时偏移，正常销售窗口被错误禁用或提前显示可购买；最终后端仍会校验。
- 根本原因：接口的业务时区在前端解析层丢失。
- 最小修改方案：已为后端无时区 SQL 时间补上固定合同的 +08:00；保留已有显式偏移的 ISO 时间。
- 需要补充的测试：UTC、America/Los_Angeles、Asia/Shanghai 三时区下分别验证开售前、开售中和结束后；原用例失败、修复后 22 项 commerce 单测全部通过。
- 是否阻塞合并：修复前阻塞；当前已有对应验证，不再构成代码阻塞。

## [P2] 登录返回地址可用编码绕过认证/API 路径限制（已修复）

- 最小修改方案：已校验解码后路径，拒绝双重编码歧义、认证和 API 返回；非 SPA 的合法同源页面执行完整文档导航。

## [P2] 只读开发预览允许有副作用的 GET 和越界代理目标（已修复）

## [P2] 离页后的搜索计时器和迟到清理函数仍能影响新页面（已修复）

- 文件与位置：frontend/src/pages/home.js：搜索 debounce 与 cleanup；frontend/src/app.js：render
- 所属维度：异步正确性、资源生命周期
- 问题：页面加载尚未返回清理函数时离开，旧计时器可能存活；迟到返回的 cleanup 未被调用。
- 触发条件：在慢目录请求期间输入搜索，再迅速切换到兑换等页面。
- 实际影响：旧搜索回调可能将用户再次导航回首页，或留下无效监听/计时器。
- 根本原因：清理只依赖已完成页面的返回值，没有覆盖挂载尚未完成的取消路径。
- 最小修改方案：已让页面监听 abort 清理，并在挂载结束时检查旧 signal、立即执行迟到 cleanup。
- 需要补充的测试：浏览器 leaving a still-loading catalog 场景确认离页后不会发生搜索导航；已经 abort 的商品/订单挂载不做 DOM/API 工作。
- 是否阻塞合并：修复前阻塞；当前已有对应验证，不再构成代码阻塞。

## [P2] 静态错误响应被长期缓存，且切换配置会丢失结算请求限制（已修复）

- 文件与位置：deploy/download-nginx.conf.example：/ui/、/pub/、/user/(api|pay)/
- 所属维度：可靠性、性能、安全、发布回归
- 问题：旧线上配置对 /ui/ 的所有状态强加一年 immutable；初版独立静态配置没有保留原 PHP 下单/收银台 64 KiB 限制。
- 触发条件：浏览器先请求不存在或未上传完成的指纹资源，或发送超过 64 KiB 的结算请求。
- 实际影响：404 可被缓存，修复文件后客户端仍不可用；原受限接口继承过大的全局请求体上限。
- 根本原因：缓存没有按成功状态区分；代理整合时遗漏接口级既有约束。
- 最小修改方案：已仅为存在的指纹文件加 immutable，缺失保持 404；公开文件错误也不加 public 长缓存；API/收银台恢复 64 KiB 限制，私有 API 与文档 no-store。
- 需要补充的测试：真实 nginx 验证 missing.js/未知版本/缺失公开文件不长缓存；两类 64 KiB+1 请求已由 200 红转为 413；正常 API 方法、状态、query 和旧 PHP CSP 保持。
- 是否阻塞合并：修复前阻塞；当前已有对应验证，不再构成代码阻塞。
