## [P1] 同场景图片覆盖 session 槽，正确验证码仍被拒绝（已修复）

- 文件与位置：原 PHP `app/Util/Captcha.php`、所有 graphic captcha 调用方；前端 `src/captcha.js`、`pages/auth.js`、`pages/product.js`
- 所属维度：正确性、并发、鉴权、协议设计
- 问题：一个 scene 只有一个可覆盖的 session 答案；表单没有图片 ID。旧校验还把输入转为整数并拒绝 0。
- 触发条件：同一会话生成两张同 scene 图片、多个标签页或刷新响应交错；旧图片答案为 `0000`。
- 实际影响：固定公开 PHP 源码中第一张图的正确答案失败、第二张通过；`0000` 恒失败。用户报告的“正确输入仍报错”存在可稳定复现的实现原因，但不声称已经还原其唯一浏览器操作序列。
- 根本原因：图片与提交之间没有不可变的 challenge 身份，加上有损整数转换；仅刷新图片不能消除共享状态问题。
- 最小修改方案：按 xianyu 登录协议返回随机 `X-Captcha-Id`，提交 `captcha_id/captcha_code`，PHP 临时私有 SQLite 中按 scene/IP/TTL 原子单次消费；四位无歧义字符、不区分大小写。SPA 与活跃 PHP 后台/安全页只共用一个加载模块；不加 session fallback 或 User-Agent 豁免，不改业务库和邮件/SMS 最终验证码。
- 需要补充的测试：已覆盖多图片/多标签、正确/错误/大小写/空白/数组、到期/重放/跨 scene/IP、限流和容量回收、两进程争抢、文件权限、真实 PNG、所有调用方及 TOTP。浏览器断言可见图片 ID 与 POST 一致，无 session cookie 也能验证。
- 是否阻塞合并：修复前阻塞；代码回归已通过。上线必须同步替换前端和 PHP，旧标签页需要刷新。

## [P2] 验证码解码不响应 fetch 取消，超时后仍永久加载（已修复）

- 文件与位置：`frontend/src/captcha.js`：refresh 的 image.decode 等待和 finally 清理
- 所属维度：可靠性、取消、资源生命周期
- 问题：只 abort fetch 不会结束浏览器图片解码 promise；尚未接管的 object URL 只能在永不结束的 finally 中释放。
- 触发条件：HTTP 返回有效 PNG 后解码迟迟未结束，或期间用户刷新/离页。
- 实际影响：新增回归在快进 10 秒后找不到失败提示，仍处于加载态；未完成图片 URL 不能及时释放。
- 根本原因：超时边界没有覆盖整次加载的异步阶段。
- 最小修改方案：同一个中断 promise 与响应、正文、解码分别竞速，结束时移除中断监听并释放候选 URL；迟到结果仍受 sequence 保护。
- 需要补充的测试：解码挂起 → 超时提示/URL 释放 → 手动重试 → 旧解码结束不覆盖新图，已红转绿；完整浏览器回归再次通过。
- 是否阻塞合并：已修复并验证，不再阻塞。

## [P2] 生产缺少受信代理配置会让新验证码限流全站共用（已修复上线）

- 文件与位置：现有 `app/Util/Client.php` 的 getClientMode/getAddress；`runtime/mode`、`runtime/trusted_proxies`；nginx proxy_set_header
- 所属维度：生产配置、正确性、安全、可靠性
- 问题：现网没有这两份 runtime 配置，也没有启用 Apache RemoteIPHeader；Client 默认读取 REMOTE_ADDR。
- 触发条件：按 IP 绑定/限流的新验证码通过 nginx → PHP 提供给多个访客。
- 实际影响：隔离复现中两个不同 X-Real-IP 都返回 `127.0.0.1`；若原样发布，全站会共用 60 张/300 秒额度，而非各访客独立预算。
- 根本原因：应用已有安全代理解析能力，但部署没有启用该配置；之前绕过真实代理的调用方替身不能发现这个问题。
- 最小修改方案：随发布保存前置状态，设置已有 mode=1 和仅回环的 trusted_proxies；nginx 继续覆盖 X-Real-IP/X-Forwarded-For 并清空上游 CF 头。不复制 Client 实现、不扩大信任网络、不信任访客自填头。
- 需要补充的测试：真实 Client 的 IPv4/IPv6 回环、不同客户端、伪造头和非受信 peer；真实 nginx 的验证码/认证路径头覆盖；部署后用两个测试地址验证独立身份。前两类已加入回归，实机结果见发布记录。
- 是否阻塞合并：已随成套发布启用，并用两个 TEST-NET 客户端地址核验各自 challenge 的 IP 绑定，不再阻塞。未来部署不得遗漏此配置。
