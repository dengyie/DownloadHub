# Findings

## [P0] 生产 MySQL 系统表空间损坏导致启动循环（已恢复）

- 文件与位置：生产 `/var/log/mysql/error.log`；原 `/var/lib/mysql-dl`。
- 所属维度：可靠性、数据完整性。
- 问题：InnoDB 报 `MY-011906`，space=0、page=5 损坏或读取失败，反复崩溃。
- 触发条件：启动原数据库。
- 实际影响：商店无法可靠访问数据库，错误日志增长至约 11.5GB。
- 根本原因：原物理数据页已损坏，不能用连接配置或重启修复。
- 最小修改方案：停循环、完整冷备；隔离副本只读抢救并逻辑导出；恢复到干净 datadir，保全原账号授权后切换。已执行，旧库未删除。
- 需要补充的测试：已完成 13 用户库、140 表的行数与校验和对照，正常模式启动、原账号连接和表检查。
- 是否阻塞合并：不阻塞代码；原数据故障已修复，宿主风险见下一项。

## [P1] 宿主 OOM 持续终止数据库进程（未解决，外部阻塞）

- 文件与位置：生产内核 OOM 记录、MySQL Supervisor 状态。
- 所属维度：生产可靠性。
- 问题：内核记录 `eci-agent invoked oom-killer` 并对 mysqld 发出 SIGKILL。
- 触发条件：宿主内存压力；不是仅由本实例使用满其 4GB cgroup 限额触发。
- 实际影响：MySQL 重启窗口内商店可能不可用，无法保证持续备份每轮成功。
- 根本原因：宿主级资源压力；观察时 cgroup 使用约 1.09GB/4.19GB，failcnt=0。
- 最小修改方案：已限制 MySQL 缓存/连接，RSS 降至约 103MB，但 OOM 计数仍增加。用户决定保留宿主；先收紧本应用进程池并量化实际退出频率，不调整 OOM 优先级或其他服务。应用优化不保证消除宿主压力。
- 需要补充的测试：目标稳定环境至少完成连续负载/重启观察、备份与恢复和公网站点探针；本机短时 200 不构成稳定性证明。
- 是否阻塞合并：不阻塞代码合并；阻塞“生产稳定性全部通过”的结论。

## [P2] 重复兑换可使未扣次凭证持续积累（已修复）

- 文件与位置：`grant_store.go` 的 `create`、`cleanup`。
- 所属维度：性能、资源边界。
- 问题：100 资源卡每分钟可创建约 2000 条凭证，原维护每分钟仅清理 500 条。
- 触发条件：持有效低额度卡持续重复兑换，不需要真的扣次。
- 实际影响：数据库和磁盘持续增长。
- 根本原因：只有按 IP 限流，没有按卡的存储容量约束，清理吞吐固定。
- 最小修改方案：同一事务限制每卡 500 条未扣次记录；维护在 3 秒总预算内按批追赶，不删除有效凭证以腾容量。
- 需要补充的测试：已覆盖跨连接争抢最后一个位置、过期记录仍计入上限、1200 条多批清理、取消及 HTTP 429。
- 是否阻塞合并：已修复，不阻塞。

## [P2] 同页打开文件会丢失最后一次授权的恢复入口（已修复）

- 文件与位置：`web/redeem.js` 的资源按钮事件。
- 所属维度：正确性、交互。
- 问题：签发后自动同页导航，而恢复凭证只存在页面内存。
- 触发条件：浏览器预览 TXT/PDF/图片或上游返回 HTML 错误页。
- 实际影响：额度已经归零，用户离开兑换页后无法找回该恢复凭证。
- 根本原因：下载导航与持有凭证的页面生命周期冲突。
- 最小修改方案：签发后显示显式的新页下载链接，保留兑换页和同凭证恢复按钮。
- 需要补充的测试：已覆盖真实 DOM 的零余额签发、不自动导航、新页链接属性、再次恢复仍发送同一凭证。
- 是否阻塞合并：已修复，不阻塞。

## [P1] 固定资源地址被 CDN 缓存为错误页面（已修复代码）

- 文件与位置：`web_embed.go`、`http_handlers.go` 的静态资源路由；线上 `/assets/redeem.js`。
- 所属维度：发布正确性、缓存。
- 问题：公网曾返回 18584 字节的“页面没有找到”HTML，状态 200、缓存 14400 秒，无法作为 JS 执行。
- 触发条件：旧 nginx 未代理新资源，CDN 在旧路由上缓存响应；仅给新源站响应补 no-store 无法撤回旧缓存。
- 实际影响：兑换页脚本无法运行。
- 根本原因：固定名资源没有版本边界，发布未验证 CDN 实际正文。
- 最小修改方案：JS/CSS 响应 no-store；HTML 使用由资源内容 hash 生成的版本参数，避开既存错误缓存。
- 需要补充的测试：已覆盖页面引用版本化资源、版本化 URL 可取到正确资产；上线还需核对公网正文 hash 和内容类型。
- 是否阻塞合并：代码已修复；版本化资源上线探针须通过。

## [P1] nginx 配置检查与重载返回成功不代表配置生效（已处理）

- 文件与位置：生产 nginx 主错误日志、`deploy/download-nginx.conf.example` 的 listen 变更。
- 所属维度：发布可靠性。
- 问题：从 wildcard :80 改为 loopback 时，新 socket 与旧 socket 冲突；日志显示 `bind() ... failed (98)`，旧 worker 继续服务。
- 触发条件：直接对上述 listen 变更执行 reload。
- 实际影响：新 assets 路由、健康接口拦截和安全日志均未实际生效。
- 根本原因：只检查命令退出和语法，没有验证运行时监听、worker 与 HTTP 行为。
- 最小修改方案：在配置检查通过后受控重启 nginx，释放旧 socket；实际 HTTP 确认 assets 正文与 `/ready` 404。
- 需要补充的测试：已核验源站真实响应；后续监听地址变更必须检查 worker、监听及业务路由，不能仅用 nginx -t 作为发布通过条件。
- 是否阻塞合并：已处理，不阻塞代码。

## [P1] OpenList 返回本机地址且签名永不过期（已修复配置）

- 文件与位置：OpenList `config.json` 的 `site_url`、`link_expiration` 设置。
- 所属维度：集成正确性、安全边界。
- 问题：实际 raw_url 指向 `127.0.0.1:5244`，签名时间戳为 0。
- 触发条件：按原配置签发下载 URL。
- 实际影响：公网用户无法访问本机地址，且旧签名无自然到期。
- 根本原因：公网站点地址为空，链接有效期沿用默认 0。
- 最小修改方案：配置真实 HTTPS 域名，签名 1 小时、网关恢复窗口 10 分钟；OpenList 仅绑定 loopback。未轮换现网签名密钥，避免无依据撤回旧链接。
- 需要补充的测试：已验证真实 HEAD/Range、过期 401；隔离实例验证重启与密钥轮换，生产确认新 URL host 和剩余寿命。
- 是否阻塞合并：已处理；历史永不过期 URL 不会因新设置自动失效，必须明确这一限制。
